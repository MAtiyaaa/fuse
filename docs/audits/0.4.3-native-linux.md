# Fuse 0.4.3 — The Native Update: Linux presentation parity

This is the **first Linux quality patch**, not a completed native-app rewrite or a claim of
Android-equivalent performance. Fuse already shares the entire Compose UI, domain model, and
Fuseline across Android and desktop. Keeping them shared avoids two diverging implementations.

## Changes in this patch

- Linux Automatic quality no longer classifies a machine with at least 6 GB RAM and four
  CPU cores as a low-quality *presentation* solely because its CPU has four cores.
  The actual device capability (and CPU-core count) remains unchanged.
- Linux desktop image-loader cache sizing checks RAM instead of using the CPU-influenced
  device tier, preventing unnecessary 1920 px bitmap ceilings on well-equipped handhelds.
- Linux hero art uses its configured native-presentation long-edge decode budget instead of
  the shared default 85% long-edge scale. Android, Windows, and macOS retain that default.
- A genuine software-rendering fallback still disables costly effects, but does not
  reduce Linux art resolution just because Skiko could not initialize GPU acceleration.
- Actual software-renderer fallback is logged with diagnostic instructions, rather than
  making the low-quality presentation indistinguishable from a user choice.
- Cross-platform policy tests exercise Linux four-core/8 GB, software renderer,
  Android/other-desktop unchanged behavior, explicit Low Power and truly low-memory devices.

No game launcher, save folder, database, or sync data changes are involved.

## Why this is not a complete Linux-native replacement

This code still uses the desktop JVM/Compose Desktop/Skiko, with Linux-native platform
services and controller input. Replacing its renderer or window host is a separate, risky
project and should be justified by real measurements; rewriting the shared UI would defeat
identical feature/behavior goals. Neither GPU acceleration nor consistent compositor-vsync
can be guaranteed by an app when the user's graphics driver and compositor cannot supply it.

## Acceptance checks before calling 0.4.3 finished

1. Compile and run `:core:model:desktopTest`, `:ui:designsystem:desktopTest`,
   `:ui:shell:desktopTest` and desktop packaging, then Android compilation and smoke tests.
2. Run Linux in GPU and deliberately forced software modes. Confirm the displayed
   renderer, do not infer acceleration merely from an OpenGL API name.
3. Compare identical screen captures against Android at the **same physical pixel dimensions**
   and equivalent content/asset sources: Home, Library, Systems, Settings and navigation layers.
4. Trace end-to-end controller input through UI handling **and frame presentation**;
   `--trace-ui` reports CPU-side rendering, not compositor-presented latency.
5. Test SteamOS Game Mode and Desktop Mode, KDE/GNOME Wayland/X11, a 4K display,
   a native handheld display and refresh rates including 60/120 Hz.
6. Run Fuseline 4 animation benchmarks with real GPU rendering and test input repeat,
   rapid tab switching, scrolling and backdrop swaps under load.
7. Only if measurements show Skiko/AWT is an irreducible bottleneck, prototype a
   separately packaged **Linux-only host** that consumes the same shared model and UI
   (or prove the need for a second renderer); never silently fork feature implementations.

## Known limitations

No physical Linux handheld, monitor, or compositor was available for this branch.
The host rendering/presentation path, Linux joystick driver and actual GPU fallback
behavior have not been physically tested or replaced by this patch. Renderer quality
changes cannot increase the pixel dimensions of an inherently small source image.
Do not publish this as a fully validated 0.4.3 native release.
