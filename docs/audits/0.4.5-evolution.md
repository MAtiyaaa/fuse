# Fuse 0.4.5: The Evolution Update

Engineering record for 0.4.5: what changed, how it was measured, what was verified and how, and what
is not done. It builds on 0.4.4.2 (`d08e0463`). Every number here comes from runs on one machine
and is given with how it was made. Nothing in this record was measured on a phone, a handheld, a
TV, Windows or macOS.

Fuse Native (an integrated runtime for Windows games on Android) was part of the plan for this
release and was dropped from it before work began. Nothing of it is in 0.4.5; the plan stays in
[docs/plans/fuse-native.md](../plans/fuse-native.md).

## 1. Causes established and changed

| Cause (found by measuring or reading) | Consequence | Change |
| --- | --- | --- |
| Search split every name into words, made three substrings per word and new rows for each typo check, for every game on every key | p95 366 ms at 10,000 games (profiled during development) | Names taken apart once when the index is read; typo rows kept by the search; letters a word lacks rule names out first. Every score is the same: `SearchRankEquivalenceTest` compares 400,000 random pairs against the old ranking |
| The search index was read only when a search started, and with every game's stored details (descriptions included) | The first search paid for reading the whole library; tens of MB of text held | Built once Home settles and again in the background 1.5 s after the library last changed; details read only for a `developer:` search; a search after a change builds it then, so it never answers from an old library |
| SQLite, without statistics, took the index on `game.missing` (false for nearly every game) as narrowing | A series' first game read every game once per series (25,000 games: 2.5 s before Home showed); Home's rows sorted the whole library instead of reading the latest in order | The 28 reads of present games write `+missing = 0`, the same condition kept off that index; the index stays for the few missing games; no schema change. `QueryPlanTest` plans every query in the schema and fails if one goes back |
| Every screen asking for a list of games built its own: every game and three rows of art per game each time | Opening the library again at 10,000 games: 361 ms at the median, 510 ms at p95 | Lists are shared per query (at most 24) and kept for 30 seconds after the last screen leaves. A write to a game or a collection lets every kept list go at once (a synchronous listener on the writing thread), so a read straight after adding or removing a game reads afresh; CI caught the first version of this handing back a list from before a removal |
| Art rows were read with every column, grouped with a key made per row, and each row's kind and source parsed by copying the enum's whole array | About 250 ms for the 30,000 rows of 10,000 games | Ten columns, runs cut as they come, kept enum entries. 10 to 15 percent less; the rest is SQLite stepping rows |
| Series detection, suggestions, disc identification and the index ran whenever they were set off, all at once | Bursts after a start or a scan competed with Home and search for the processor and the one database connection | `BackgroundWork`: at most two at once on threads of their own, waiting while a game runs or the device sleeps, with each job's cost kept for the Observatory |
| Library folders were looked at on start, on resume and when asked | A game copied in waited for the next start | `FolderWatch`: each library folder and the system folders in it followed with the system's change notices (`WatchService` on computers, `FileObserver` on Android); saves, states, partial downloads and hidden files ignored; a quick scan once a folder has been quiet for two seconds, held while a game runs |
| Library Health (new in this release) ran after every scan, start included | At 25,000 games it read 75,000 picture paths and whole-library queries on the one connection while the first searches ran | It runs only when System health is opened or after a repair (found by the before and after benchmark, fixed before release) |
| Pausing a transfer marked it paused without waiting for it to stop | A resume straight after could race the old download still closing its partial file (a CI run caught the test version of this) | Pause and Pause all wait for the transfer to stop, as Cancel already did, and record the bytes that arrived |
| Fuse One's settings arriving and a choice in the interface each read Fuse's settings and wrote them back in two steps, and the writer saved the value it was sent rather than the newest | A choice made at that moment could be put back, and the newest value could go unsaved (`ChoicesDuringWritesTest` caught it once in CI; over 150 local rounds, most under full load, did not) | Both change the settings in one step (`update`), and every write saves what Fuse shows at that moment |

## 2. Added

- **Performance Observatory** (Settings, Display; System health, Diagnostics): two seconds of Fuse's
  own frames (rate, median, p95, p99, worst, missed refreshes against the display's interval),
  timed reads of the real library (Home's counts, every game read for search, a search), what the
  picture caches hold, each background job's runs and cost, Fuse's working memory and what the
  system reports; measured again on request, and a report to copy or save with no names in it.
  Nothing of it runs while it is closed.
- **Library Health** (System health): pictures whose files are gone (repaired after a confirmation
  that says what changes; pictures the person chose are never changed), pictures of games no longer
  in the library (tidied after a confirmation; files stay), games without a cover, and the same
  file in two places (listed, never merged).
- **How It Runs Here**: per-game compatibility in the person's own words, with standings that never
  call a game playable because it started (Plays well, Plays with problems, Launches here and not
  confirmed, Doesn't work, Untested), each with the emulator its last session here used, the Fuse
  version and the kind of device, and a report to copy or save. Nothing of it leaves the device.

## 3. Large-library benchmarks: 0.4.4.2 against 0.4.5

`LibraryScale` (`ui/shell/src/desktopTest/.../perf/LibraryScale.kt`) builds a library of 100,
1,000, 5,000, 10,000 and 25,000 games across eleven systems, every game with a cover, a logo and
a background drawn from a pool of real images on disk, some favourites and play history, and then
measures through the real store over the real database. It was run on 0.4.4.2 (the same file
copied into a worktree at `d08e0463`) and on 0.4.5, one after the other, on one machine (the 0.4.5
run's copy adds 40 searches at the very end, once settled, which 0.4.4.2's run did not make): OpenJDK
21.0.12, Linux, four cores of an Intel Xeon at 2.8 GHz, 15 GB. Each figure is one run; where other
0.4.5 runs differed notably, that is said.

`./gradlew :ui:shell:desktopPerf --tests '*LibraryScale*' -Pfuse.perf.dir=<folder>`

The tables are from the run before kept lists were let go on writes (the last change before
release). Run again at 10,000 and 25,000 games with it, the library opened again still took 0.04
and 0.03 ms at the median: nothing in those steps writes to a game or a collection.

What the numbers say, and what they don't:

- **Home after start** at 10,000 and 25,000 games is the series fix: 1.0 s to 0.13 s, and 2.5 s to
  0.22 s. At 100 to 5,000 games Home was already quick and the difference is within the run to run
  spread (a second 0.4.5 run measured 162 ms at 100 games, the first size after the JVM starts).
- **The library opened again** is the shared list: it is already there, so the time is a lookup.
  **The first open** is still a read of every game and its art (see Known limitations).
- **Search while typing** in 0.4.5 began about a second after start, while the start's own work
  (series, suggestions, the index) still ran; in 0.4.4.2 the steps before it took up to 24 s, so its
  searches ran once everything had settled. 0.4.5's settled columns are the like-for-like figure
  for those. The first search right after start waits for the index (built 1.5 s after Fuse
  settles), so at 1,000, 10,000 and 25,000 games it is slower than 0.4.4.2's first search, made 1
  to 24 s later: 590 ms against 341 ms at 25,000. A second 0.4.5 run measured a typing p95 of 399 ms at
  25,000 games (82.7 ms in this one): the moment shares one database connection with the start's
  work, and how they interleave varies.
- **Full scans** did not change in this release; across three 0.4.5 runs at 10,000 games they took
  3.8 s, 4.0 s and 5.3 s against 3.7 s, which is this machine's spread rather than a measured
  change.
- **Heap held** is larger: the search index (every name taken apart once) and up to 24 shared
  lists are kept, 43 MB at 25,000 games against 14 MB.
- **Background work** at 25,000 games right after start, from the Observatory's own record:
  finding series 607 ms, suggestions 524 ms, the index 498 ms, all off the thread that draws.

## 5. Reliability: checked rather than rebuilt

The plan asked for several things Fuse already had. Each was read in the code and its tests rather
than rebuilt:

- **Fuse One save integrity**: every file hashed (SHA-256) into a content store; downloads checked
  against their hash, staged beside the target and moved into place atomically, the files already
  there kept first as a revision; a durable outbox of revisions with the device that made each;
  conflicts settled by the person, never by a newer clock; blank (all zero or 0xFF) saves never sent
  as the newest and told about once; a save still being written during play not sent until it has
  been left alone for a look. `core/sync` has 54 test files and 384 tests.
- **Play time**: time with the screen off or the computer asleep is taken off (`SessionClock`),
  and a session Fuse didn't see end ends where it was last seen alive (heartbeat), not at the next
  start.
- **Crash recovery**: starts that never settle are counted; after repeated ones Fuse starts in safe
  mode with nothing automatic running (`StartupGuard`). The database is copied before every
  migration, and an older Fuse opening a newer library gets the copy back with the newer one kept
  beside it. The schema is unchanged in 0.4.5 (version 8).
- **Performance profiles per game**: each game's own emulator settings (renderer, resolution and
  the rest, in the emulator's own files) from its options; device-wide profiles in Settings.
- **Smart lists**: Unplayed, Barely played, Gathering dust, Play together, Added lately, Favourites,
  pinnable among the Library's tabs.
- **Emulator verification**: Fuse Intelligence's steps (detected, installed, can run, set up, launch
  verified) per emulator, each only on evidence seen on this device.

## 6. Verification

New tests in 0.4.5, each run locally and in CI:

| Test | What it proves |
| --- | --- |
| `SearchRankEquivalenceTest` (core:data) | The new ranking gives every score the old one gave, over 400,000 random name and query pairs, and a reused needle answers as a new one |
| `QueryPlanTest` (core:data) | SQLite plans every labelled query in the schema; only the list of missing games goes through `game_missing`, and a series' first game is found through the series |
| `MediaRepositoryTest` (core:data, added case) | Art read in runs per owner is the same as art read owner by owner, over 1,700 owners |
| `LibraryHealthTest` (core:data, 3 cases) | Each repair changes only what it names: web pictures go back to their address, pictures without one are forgotten, chosen pictures stay, games in the library keep their art |
| `HealthStoreTest` (ui:shell, added case) | Library Health through the store: pictures whose files are gone are found and put right |
| `FolderFollowTest` (ui:shell) | A game copied into a followed folder is in the library without a scan being asked for; saves and partial files are not |
| `ObservatoryTest` (ui:shell) | Frame statistics and missed refreshes from known intervals |
| `CompatStoreTest` (ui:shell) | Each standing, and that play time brought in from elsewhere proves nothing here |
| `TransferTest` (core:transfer, changed case) | A paused transfer keeps exactly the bytes it counted, and resumes to a whole, checked file |

CI (`ci.yml`) runs every module's desktop tests on JDK 17 and builds the Android app. The Android
app is compiled, not run: `AndroidFolderWatch` has not been on a device. Screens added in this
release (the Observatory, How It Runs Here) were rendered by the audit harness
(`./gradlew :ui:shell:desktopAudit`) and the screenshots looked over.

## 8. Known limitations

- **The first library open after start** reads every game and its art: 0.39 s at 10,000 games and
  1.0 s at 25,000 in the run above. Opening it again is instant (shared lists), but the first
  time is SQLite stepping rows, which this release only trimmed.
- **Searching in the first seconds after start** at 25,000 games shares the processor and the one
  database connection with the start's own work (series, suggestions, the index): the first
  search waits for the index, and some searches wait for the connection. Once that work ends
  (seconds), searches answer in tens of milliseconds. 0.4.4.2 was never measured at that moment:
  in its run the steps before searching took 24 s.
- **Folders followed** are a library folder and the system folders in it, not every folder below:
  a file added inside a game's own folder (a disc of a multi-disc game) waits for the next scan.
  Network shares and some removable drives may not send change notices; starting Fuse, coming back
  to it, and Rescan still find everything.
- **Full scans** were not a goal of this release and their code is unchanged; see the scan table
  for how they measured.
- **Nothing was measured on hardware** other than this machine: no handheld, phone, TV, Windows or
  macOS figures are claimed.
